## 操作性
- 利用者はITに詳しくない一般社員を含むため、PC向けの標準的なWeb画面とし、ラベル・エラーメッセージは日本語で平易に表示する。
- 申請の状態は色とテキストの両方で表示する。期限超過は一覧で目立たせる。
- 対応ブラウザは社内標準ブラウザの最新版（Chrome・Edge）。スマートフォン向け最適化は対象外。

## 処理量・性能
- 同時接続数：最大10ユーザー程度。備品数百点・履歴の年間増加は数千件程度。
- 応答時間：一覧・検索・申請系の操作は通常時3秒以内（目標値）。CSV一括登録（1,000行）は30秒以内。

## 可用性・信頼性
- 整合性：同一備品に対する承認・貸出処理は、DBのロック等により排他制御し、同時操作でも二重貸出を発生させない。
- 稼働時間：平日の業務時間帯に利用可能であればよい。稼働率の数値目標は設けない。
- バックアップ：データベースを1日1回バックアップし、直近7世代を保持する。
- 復旧：障害時は運用者がバックアップから復旧する。復旧時間の目安は当日中。冗長化は行わない。

## 将来の拡張
- 利用者・備品の増加はレイヤー分離（エンドポイント・業務処理・DB操作の分離）により対応する。
- 対象外とした機能（延長申請・外部通知・SSO・写真等）は、機能追加として設計を分離して後から追加できる構成とする。
- メール通知を追加する場合に備え、通知の生成処理は1か所に集約する。

## セキュリティ
- 実装レベルのルールは`運用ルール/開発ルール/セキュリティルール.md`に従う。
- パスワードはArgon2idでハッシュ化して保存する。パスワードは8文字以上。
- 認証トークンには有効期限を設ける（アクセストークンの有効期限は8時間程度）。ログアウト・ユーザー無効化・パスワード変更等では、サーバー側のトークン世代管理により以降のリクエストが拒否されること（機能要件「アクセス制御」参照）。
- 認証失敗が続く場合の総当たり対策として、ユーザーIDごとに連続失敗5回で15分間ロックする。
- 入力値はサーバー側で型・必須・長さ・形式を検証する。SQLはORM・プレースホルダを使用する。
- 通信はHTTPSで暗号化する（社内認証局または自己署名証明書による。判断根拠書No.8）。
- ログにパスワード・トークンを出力しない。秘密情報（DB接続情報・署名鍵・初期管理者情報）は環境変数で管理し、リポジトリへ含めない。
- 認可（管理者専用機能の制限、他人データの参照制限）は、画面の表示制御だけでなくAPI側で必ず検証する。

## 動作環境
- サーバー：社内LAN内の1台（Linux または Windows + Docker）。Docker Composeでフロントエンド配信・バックエンド・DBの各コンテナを起動する。
- ネットワーク：社内LANのみ。インターネットからの直接アクセスは受け付けない。
- 利用端末：社内のPC。ブラウザは操作性の項に記載のとおり。

## テスト方針
- 単体テスト：バックエンド（pytest、DBに依存しない）とフロントエンド（Vitest + React Testing Library）で行う。
- 結合テスト：バックエンドAPIを実DB（PostgreSQL）で行う。認証・認可・入力値検証・二重貸出防止・状態遷移を対象に含める。
- セキュリティに関わる処理（認証・認可・入力値検証）は単体・結合テストの対象に含める。

## 運用・保守
- 運用体制：管理者（備品担当者）が日常運用（承認・貸出・返却・マスタ管理）を行う。システムの起動停止・バックアップ・復旧は、社内の情報システム担当が行う。
- 依存パッケージの更新方針：既知の脆弱性の有無を四半期に1回確認し、必要に応じて更新する。
- 障害・不具合時：運用担当が状況を確認し、復旧または開発者へ連絡する。
- 期限通知の判定・ノーショー自動取消は、システム内の日次処理（アプリ内スケジュール）で毎日6:00（JST）に実行する。バックエンドは1プロセスで起動し、日次処理の二重実行を防ぐ。
